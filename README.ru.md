# agent-harness-template

Универсальная болванка репозитория для разработки с агентами (Claude Code). Основана на идее harness engineering: надёжность агента определяется не промптом, а окружением вокруг модели. Здесь это окружение собрано в файлы, которые копируются в любой проект.

## Что внутри в двух словах

- **Контракт задачи** до первой строки кода (Gate 1: ты утверждаешь скриптом `approve.sh`, до этого хук не даёт агенту править код).
- **Проверки по лесенке** от дешёвых к дорогим: lint, build, unit, arch, ui.
- **Агент-критик** на более сильной модели (opus), в свежем контексте, только для чтения. Его задача найти повод отклонить результат.
- **Receipt** в конце: только то, что система может доказать (Gate 2: ты читаешь и решаешь про коммит).
- **Жёсткие стопы** (деплой, релиз в App Store, миграции) лежат в хуках и permissions, а не в промпте.
- **Модель проекта** закреплена в `.claude/settings.json` и сверяется хуком при старте сессии, поэтому `/model` в соседнем проекте сюда не протекает.
- **Advisor** (опционально): более сильная модель, к которой основная обращается в точках решения. Закреплён в `.claude/settings.json` так же, как модель.

## Быстрый старт

```bash
cp -R agent-harness-template/. /путь/к/проекту/      # или используй как GitHub-шаблон
cd /путь/к/проекту
chmod +x scripts/*.sh profiles/*/*.sh .claude/hooks/*.py
./scripts/init.sh                                   # имя, профиль (generic/ios), модель, команды, vault
./scripts/check.sh                                  # посмотреть, какие шаги настроены
python3 .claude/hooks/test_guard.py                 # проверить хук Gate 1 на своей машине
```

Obsidian не обязателен: на вопрос про vault в `init.sh` просто нажми Enter, путь останется пустым, и синхронизация ничего не делает. `init.sh` запускай в проекте, созданном из шаблона, а не в самом репозитории шаблона: он записывает локальные пути в `harness.yml`.

Дальше в Claude Code, внутри проекта:

```
/task добавить X          -> создаётся tasks/<дата-слаг>/contract.md (status: DRAFT), contract-reviewer даёт совет, агент останавливается
                             ты читаешь контракт, отвечаешь на открытые вопросы
./scripts/approve.sh      -> в СВОЁМ терминале (не через агента): контракт утверждён и заморожен, код разблокирован
                             агент работает, ведёт state.md
/gate                     -> check.sh --full, затем критик; на REJECT агент чинит и повторяет (до лимита)
/receipt                  -> tasks/<id>/receipt.md и черновик pr.md; код снова заблокирован, агент останавливается
                             ты читаешь receipt и сам коммитишь
/retro                    -> если сбой можно было предотвратить: диагноз + одно улучшение харнесса
```

Базовый коммит нужен, чтобы в первой задаче работал `git diff HEAD`: без него у критика нет диффа, и доказательства приходится собирать руками. Если отказался от него в `init.sh`, сделай его сам до первой задачи.

Первую задачу сделай маленькой и безопасной (например, добавить тест к существующему коду). Цель первого прогона не результат, а проверить, что весь цикл работает.

## Gate 1: утверждение контракта

Раньше правило «код только после APPROVED» держалось на инструкции. Теперь его держит хук.

- `./scripts/approve.sh` ставит `status: APPROVED` в контракте и кладёт в `tasks/<id>/APPROVED` sha256 файла `contract.md`. Хук `guard.py` пускает агента к коду проекта, только пока хеш совпадает.
- Контракт после утверждения заморожен. Любая его правка (твоя или агента в обход хука) снимает утверждение: расширить scope или ослабить acceptance задним числом нельзя. Поправил контракт сам, запусти `approve.sh` ещё раз.
- Агент утвердить не может: скрипт требует терминал и отказывается работать внутри Claude Code, хук блокирует его запуск и запись файлов утверждения, в `settings.json` стоит deny. Строка `status: APPROVED`, которую агент написал сам, ничего не открывает.
- Receipt закрывает задачу: с появлением `receipt.md` код снова заблокирован. Нужна доработка после receipt: удали receipt сам или дай быстрое разрешение.
- Быстрая дорожка для мелочей: `./scripts/approve.sh --quick [N]` открывает до N файлов (по умолчанию 3, максимум 10) на 60 минут без контракта и критика. Хук считает файлы сам.
- `./scripts/approve.sh --status` показывает, что сейчас утверждено. `--revoke` отзывает утверждение.
- Без утверждения агенту всегда доступны `tasks/` и `docs/`. Список расширяется через `ungated_paths` в `harness.yml`.
- Выключатель: `require_approval: false` в `harness.yml` возвращает правило на уровень инструкции.

Запускай `approve.sh` в отдельном окне терминала. Через `!` внутри Claude Code он откажется работать, так и задумано.

## Work packages: задача по пакетам

Необязательно, включается на одну задачу. Нужно, когда задача идёт через несколько слоёв и её части можно сделать по очереди.

- В контракте есть блок ` ```scope `: по строке на пакет, `P1: glob, glob`. Пустой блок означает обычную задачу, всё работает как раньше.
- После утверждения хук пускает правки кода только в эти глобы. Блок входит в хеш контракта, расширить его можно только через `approve.sh --revoke`, правку и новое утверждение. `approve.sh` при утверждении печатает пакеты, которые будет держать хук.
- `/work` ведёт пакеты по одному: записывает номер пакета в `tasks/<id>/.package`, запускает субагента `worker`, читает его заметку `tasks/<id>/packages/<ID>.md`, запускает проверку пакета. Воркер, которому нужен файл вне пакета или у которого два требования контракта несовместимы, останавливается со статусом BLOCKED, и вопрос идёт к тебе.
- После последнего пакета оркестратор проходит по всем пунктам acceptance и ищет названное доказательство в логах, а не в заметках. Только потом задача считается готовой к `/gate`. Критик один, на весь дифф.
- Пункты про всю задачу целиком (старые тесты не тронуты, запретные пути чисты, полный прогон) принадлежат оркестратору, а не последнему пакету.

Что показали два пилота в Tapestry (ноябрь 2026): границы держатся и в субагенте, заметки передают следующему воркеру всё нужное, проход по доказательствам ловит отклонения до критика. Чего пакеты не дали: меньше раундов критика не стало, скорости тоже (воркеры идут по одному). Для задачи одного слоя на несколько файлов пакеты это накладные расходы: две заметки и передача между воркерами.

## Параллельные задачи: несколько агентов в своих каталогах

Необязательно. Нужно, когда есть две-три независимые задачи и ты хочешь, чтобы они шли одновременно. Параллельность живёт на уровне задач, а не пакетов: у каждой задачи свой каталог (git worktree), своя ветка, свой контракт, свой критик.

1. В основном окне: `/swarm <задачи своими словами>`. Агент режет работу на задачи, проверяет пересечения по файлам и пишет план в `tasks/.swarm-plan` (строка на задачу: `имя | что сделать`, а для зависимой `имя | after: другая | что сделать`). План это граф задач: `launch` поднимает только те, у которых всё, от чего они зависят, уже слито; после каждого `finish` запускай `launch` снова. Каталогов и кода он не трогает.
2. Ты в терминале: `./scripts/swarm-worktree.sh launch`. Для каждой задачи создаётся каталог `../<репозиторий>-<имя>` на ветке `task/<имя>` и открывается окно Terminal, где `claude` стартует с `/task`. В iOS-проекте у каждого каталога свой симулятор.
3. `./scripts/swarm-worktree.sh status` показывает, чего ждёт каждая задача. `./scripts/swarm-worktree.sh approve` проводит Gate 1 из этого же терминала: показывает цель контракта и вердикт ревьюера и спрашивает по каждой задаче.
4. Gate 2 как обычно: читаешь receipt и коммитишь в каталоге задачи.
5. `./scripts/swarm-worktree.sh finish` сливает закоммиченные ветки, один раз гоняет `check.sh --full` на общем результате и убирает слитые каталоги. На конфликте слияния останавливается и ничего не удаляет.

Скрипт запускает только человек: он работает вне папки репозитория. Окна открываются через Terminal на macOS; на другой системе скрипт печатает команду, которую надо выполнить в новом окне.

Что показали две пробы в Tapestry (ноябрь 2026): харнесс в отдельном каталоге работает без переделок; между Gate 1 и Gate 2 человек задачам не нужен, его время уходит на контракты в начале и на receipt и слияние в конце; конфликт в общем файле (корень сборки зависимостей, таблица в `docs/architecture.md`) решается руками за минуты. Больше трёх задач сразу не пробовали.

## Модель проекта

Проблема: `/model` с выбором через Enter пишет модель в пользовательские настройки (глобальный дефолт на всю машину), а `CLAUDE.md` и контракт модель выбрать не могут (для Claude Code это просто текст). Из-за этого переключение в одном проекте меняло модель во всех.

Как устроено здесь:

- `model:` в `harness.yml` это источник правды. `init.sh` спрашивает модель (по умолчанию `sonnet` для рутины, `opus` для тяжёлой архитектуры) и прописывает её в `harness.yml` и в `"model"` в `.claude/settings.json`. Проектные настройки приоритетнее пользовательских, поэтому проект стартует на своей модели.
- В контракте есть необязательное `model:` (по умолчанию `default`) для задачи, которой нужна другая модель. Менять модель в сессии должен человек через `/model`: агент не может.
- Хук `.claude/hooks/model-check.py` на старте сессии сравнивает модель сессии с ожидаемой (контракт `APPROVED` без receipt > `harness.yml`). При несовпадении он показывает `MODEL MISMATCH` тебе и агенту; агент обязан сказать об этом в первом ответе и не начинать работу.
- Хук только предупреждает. Заставить Claude Code переключить модель он не может, а `/model` внутри сессии приоритетнее пина.
- Если выбрать модель через `/model` в проекте, где пин другой, Claude Code может сохранить выбор в `.claude/settings.local.json` этого проекта (зависит от версии). Тогда проверяет всё тот же хук.
- Выбор модели «только на эту сессию» в пикере `/model` зависит от версии Claude Code: проверь у себя, какая клавиша это делает.

### Advisor (опционально)

`/advisor` сохраняет выбор в пользовательские настройки (протекает так же, как `/model`), поэтому он закреплён по тому же принципу.

- `advisor:` в `harness.yml` (`none`, `opus`, `fable` или полный id) это источник правды. `init.sh` спрашивает его после модели, проверяет, что advisor не слабее модели проекта (для известных имён), и пишет `"advisorModel"` в `.claude/settings.json`. При `none` ключ не пишется.
- Хук `model-check.py` сверяет только конфигурацию (`harness.yml` и `settings.json`) и при расхождении показывает `ADVISOR DRIFT`. Живое состояние advisor Claude Code хукам не отдаёт, поэтому в receipt есть строка ADVISOR: число консультаций по записям в `state.md` или UNVERIFIED.
- `advisor: none` значит только «проект ничего не закрепляет»: advisor, включённый глобально через `/advisor`, всё равно может действовать.
- Enter в пикере `/advisor` записывает выбор в пользовательские настройки, Esc отменяет.
- Advisor работает в контексте самой сессии и не заменяет независимого `critic`. В `CLAUDE.md` для него есть строка «когда звать»: без неё нет гарантии, что модель его вызовет.
- Для Fable как advisor нужны Claude Code v2.1.170+ и доступ к Fable.

Для уже существующих проектов без шаблона достаточно добавить `"model": "sonnet"` (или `"opus"`) в их `.claude/settings.json`.

| `harness.yml` | настройки: модель, advisor, Gate 1, команды проверок, бюджеты, свои стопы, защищённые и открытые пути, vault. Агент его не правит |
| `.claude/settings.json` | модель проекта, advisor, permissions (allow / ask / deny) и подключение хуков |
| `.claude/hooks/guard.py` | блокирует опасные команды, правки защищённых файлов, правки кода без утверждённого контракта (Gate 1) и правки вне блока `scope` утверждённого контракта |
| `.claude/hooks/test_guard.py` | синтетические тесты `guard.py` и `approve.sh`; запускаются одной командой |
| `.claude/hooks/model-check.py` | на старте сессии предупреждает, если модель не совпадает с ожидаемой (проект или контракт) или advisor расходится с `harness.yml` |
| `.claude/agents/critic.md` | критик: read-only, модель opus, формат вердикта ACCEPT / REJECT |
| `.claude/agents/contract-reviewer.md` | ревьюер черновика контракта: read-only, модель opus, совет перед Gate 1 (READY / REVISE), решает всё равно человек |
| `.claude/agents/worker.md` | воркер: выполняет ровно один рабочий пакет контракта в свежем контексте, пишет только в глобы своего пакета, оставляет заметку в `tasks/<id>/packages/` |
| `.claude/commands/` | `/task`, `/work`, `/gate`, `/receipt`, `/retro`, `/swarm` |
| `docs/` | `architecture.md`, `commands.md`, `release.md`: заполняются под проект |
| `tasks/_TEMPLATE/` | шаблоны `contract.md`, `state.md`, `receipt.md` |
| `.github/pull_request_template.md` | шаблон PR; `/receipt` собирает по нему черновик `tasks/<id>/pr.md` с чекбоксами «не менять» и acceptance |
| `tasks/lessons.md` | журнал уроков (flywheel), агент читает перед задачей |
| `scripts/approve.sh` | Gate 1: утверждение контракта и быстрое разрешение. Запускает только человек |
| `scripts/check.sh` | лесенка проверок, пишет `checks.log` в активную задачу |
| `scripts/evidence.sh` | сверяет имена тестов из acceptance контракта с `checks.log`: где каждый прошёл и на текущей ли сборке (`work=`). Только читает; его зовёт шаг evidence pass в `/gate` |
| `scripts/init.sh` | разовая настройка проекта |
| `scripts/swarm-worktree.sh` | параллельные задачи: `launch`, `status`, `approve`, `finish`. Запускает только человек |
| `scripts/sync-obsidian.sh` | копирует receipt в Obsidian vault (в одну сторону) |
| `profiles/` | наборы команд под стек; `ios` включает pattern-проверку архитектуры |

## Где живёт состояние

Источник правды это репозиторий (`tasks/`): он версионируется, агент читает его сам. Obsidian это копия для чтения: `sync-obsidian.sh` кладёт receipt в `<vault>/agent-runs/<проект>/`. Двусторонней синхронизации нет намеренно.

## Что реально принудительно, а что только инструкция

| Правило | Как держится |
|---|---|
| Деплой, fastlane, `xcrun altool`, `-exportArchive`, publish, миграции, terraform/kubectl apply, force push | **hook + deny** (агент физически не выполнит) |
| Правки `harness.yml`, `.claude/settings*`, хуков, критика, `.env*`, путей из `protected_paths` | **hook** |
| Запись вне папки проекта | **hook** |
| Критик ничего не меняет | **tools: Read, Grep, Glob** (нет Edit и Bash) |
| `git add / commit / push / merge / reset` | **ask**: спрашивает тебя каждый раз |
| Модель проекта | **`"model"` в settings.json задаёт модель на старте; хук предупреждает при несовпадении**. Переключение в сессии через `/model` не блокируется |
| Нельзя писать код до утверждения контракта | **hook** на Edit/Write: нужен `tasks/<id>/APPROVED` с хешем контракта или быстрое разрешение. Запись через Bash хук не видит, её держит список `allow` (всё остальное спрашивает тебя) |
| Утверждает только человек | **hook + deny + проверка терминала** в `approve.sh` |
| Контракт не меняется после утверждения | **hook** (файл заморожен) **+ хеш** (правка в обход снимает утверждение) |
| Правки кода только внутри scope контракта | **hook**, если в контракте заполнен блок `scope`: список глобов входит в хеш утверждённого контракта, агент расширить его не может. Пустой блок = проверки нет |
| Воркер правит только свой пакет | **hook по файлу `tasks/<id>/.package`**, который пишет оркестратор `/work`: защита от случайности, а не от умысла |
| DONE воркера и «готово к `/gate`» | **инструкция**: воркер ставит DONE только с названными доказательствами, оркестратор перед `/gate` ищет доказательство каждого пункта acceptance в логах |
| «Must not change» из контракта не тронуто | **критик + SCOPE CHECK в receipt и PR** (проверяется по диффу и видна ревьюеру; автоскрипта пока нет, поведение без путей остаётся на критике) |
| Нельзя ослаблять тесты | **инструкция + критик** (он проверяет это в диффе) |
| Лимиты ретраев и размера диффа | **инструкция** (`budgets` в `harness.yml`), агент следит сам |

Слабые точки, которые стоит знать. Первая: Gate 1 закрывает инструменты Edit и Write, а не Bash. Команда вроде `sed -i` по файлу проекта хуком не проверяется: её останавливает только то, что она не входит в `allow` и Claude Code спросит тебя. Если работаешь в режиме без подтверждений, этой защиты нет. Вторая: хук `guard.py` ловит команды по шаблонам, а не по смыслу. Обфусцированный вызов (например, через скрипт, который сам вызывает fastlane или пишет файл утверждения) он не заметит. Третья: `scripts/check.sh` и `profiles/` агент править может, то есть теоретически может ослабить сами проверки; это видно в диффе и остаётся на критике. Для сценария «агент не должен случайно» этого достаточно, от злого умысла это не защита.

## Кастомизация под проект

1. `./scripts/init.sh`: имя, профиль, модель, команды проверок.
2. `docs/architecture.md`: слои, направление зависимостей, куда класть новый код. Пиши коротко и проверяемо.
3. `profiles/ios/layers.rules`: добавляй правила архитектуры по одному, после реальных сбоев. Работает по шаблонам в тексте файлов. Для слоёв-модулей (SPM-таргеты) удобно ловить `import`, для слоёв-папок придётся ловить имена типов или писать XCTest-проверки и класть их в шаг `unit`.
4. `harness.yml`: `protected_paths` (например, `**/Generated/**`), свои `blocked_commands`, `ungated_paths`.
5. Новый стек: создай `profiles/<имя>/commands.yml` (см. `profiles/README.md`).

## Принципы, на которых это построено

- Контракт вместо расплывчатого запроса, доказательство вместо слова «готово».
- Сначала дешёвые детерминированные проверки, модель только там, где есть неоднозначность.
- Верификация это попытка опровергнуть, а не второе мнение: критик в свежем контексте и с правом только отклонять.
- Правило, которое важно повторно, поднимается вверх по лестнице: объяснение, чеклист, шаблон, автопроверка, принудительная политика.
- Сложность по факту сбоев. Здесь намеренно нет автоматической классификации сбоев и самообучения: сначала `/retro` вручную, и только повторяющиеся сбои превращаются в автоматику.
- Харнесс стареет. Раз в пару месяцев проверяй, какие гейты и правила уже не нужны (модели улучшаются), и удаляй их.

## Известные ограничения

- UI-тесты на симуляторе медленные и нестабильные. Они вынесены в последний шаг и идут только в `--full` и `/gate`.
- Шаг со статусом SKIP не считается пройденным: он попадает в NOT VERIFIED. Пока `arch` не настроен, критик проверяет архитектуру только по диффу.
- `init.sh` при повторном запуске не переименовывает заголовок `CLAUDE.md` (плейсхолдер уже заменён). Это правится руками.
- Скрипты проверены на Linux. На macOS они рассчитаны на стандартный bash 3.2 и `python3` из Xcode Command Line Tools, но на твоём Mac первый прогон стоит сделать самому.
- Шаблон обкатан на одном проекте (Tapestry, iOS, около 40 задач). На другом стеке первый прогон стоит считать тестом: первую задачу бери маленькой.
- `model-check.py` проверен только на синтетических входах (совпадение, несовпадение, контрактный override, отсутствие поля). Передаёт ли твоя версия Claude Code поле `model` в SessionStart, на живой сессии ещё не проверено; если не передаёт, хук скажет «не могу проверить» вместо молчания.
- Хук (Gate 1 и scope) и `approve.sh` проверены синтетическими тестами (`python3 .claude/hooks/test_guard.py`, 85 кейсов) на Linux и на macOS. В живых сессиях Claude Code в Tapestry подтверждено: хук срабатывает на правках из субагента. Не проверено: выставляет ли твоя версия Claude Code переменную `CLAUDECODE` (проверка терминала от неё не зависит).
- Проект, созданный из старой версии шаблона: после обновления `guard.py` Gate 1 включается сразу, даже если в его `harness.yml` нет ключа `require_approval`. Вместе с хуком нужно скопировать `scripts/approve.sh`.
